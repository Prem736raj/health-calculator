## A. Executive Summary
=======================

The current master branch is materially healthier than the original Sept-05 audit baseline. Many previously identified issues are already fixed: missing reminder receivers are declared, receiver coroutine work uses goAsync-style handling, FileProvider exposure is narrow, cleartext traffic is disabled, “Clear All Data” delegates to Android’s full app-data reset, notification permission checks are present, water-widget mutations are routed through a private receiver, deep-link/navigation handling is allow-listed, analytics is opt-in and parameter-allowlisted, App Check separates debug from release, release signing is externalized, and current CI runs unit tests, release lint, debug/release APK builds and an AAB build.

However, the application is NOT yet ready for a confident public health/wellness launch. The remaining blockers are not cosmetic. The highest-impact confirmed problems are:

P1-01 — Multi-profile privacy/data-isolation failure. The UI claims/seems to support independent family profiles, but weight, water, calculation history and other health records are global and do not carry profileId. Switching profiles therefore does not isolate stored health data. This can expose another local profile’s history/summary/share content.

P1-02 — Health Connect steps are read using raw StepsRecord records and manually summed. Android’s current Health Connect guidance explicitly says cumulative types such as StepsRecord should use aggregate() to avoid double counting across sources. Current code can therefore produce incorrect daily step totals/trends.

P1-03 — Blood-pressure mixed-category readings can be misclassified as hypotension. Example: 150/55 passes the low-diastolic check before the Stage 2 rule and is returned as HYPOTENSION even though current AHA classification requires the higher category.

P1-04 — Metabolic-syndrome screening treats “waist medication” as if medication can satisfy the central-waist criterion. The harmonized criteria provide drug-treatment alternatives for triglycerides, HDL, blood pressure and glucose—not waist circumference.

P1-05 — AI chat currently persists the user message to Room but does not append it to the in-memory messages StateFlow before showing the assistant bubble. The sent user message can disappear from the live conversation until reload.

P1-06 — Per-calculator CSV export can write a type-specific header but then append an arbitrary number/order of details values. Rows can have more columns than the header and values can be under the wrong headings.

P1-07 — Ideal-body-weight logic invents a proportional scaling for heights below 60 inches and continues labeling the values as Devine/Robinson/Miller/Hamwi results. That extrapolation is not part of those historical equations.

There are also important P2 issues: unsourced VO2 “fitness age”/percentile bands and recovery labels, WHR “At action point” wording below the actual threshold, hydration activity/climate additions presented with more precision than their evidence supports, BMR validator/calculation range mismatches, a fragile history-details parser, food-log day rollover that depends on opening specific screens, BP alarm timezone/DST behavior, insufficient Room migration testing, legacy 36dp interactive targets, and a near absence of instrumentation/UI/accessibility tests.

Overall production score: 7.0 / 10.
Build/CI readiness is relatively strong; medical/data isolation/runtime validation is the reason the product should not yet be considered launch-ready.

Primary recommendation:
1. Fix the P1 medical/privacy/data correctness issues first.
2. Temporarily disable multi-profile switching/sharing until records are profile-scoped.
3. Validate on real Android 13–16 devices/emulators with Health Connect.
4. Complete Play/Firebase owner-side declarations and signing.
5. Launch a closed test before production.

## F. Confirmed Bugs
===================

### P1-01 — Multi-profile health data is not actually isolated
Severity: P1 High
Category: Privacy / data integrity / product correctness

Evidence:
- `data/model/FamilyProfile.kt` describes profiles as allowing multiple users to track independently.
- `presentation/profile/ProfileScreen.kt` displays ProfileSwitcherBar and supports adding/switching profiles.
- `data/repository/FamilyProfileRepository.switchProfile()` only toggles which FamilyProfile row is active.
- `data/model/WeightEntry.kt` has no `profileId`.
- `data/model/WaterIntakeLog` has no `profileId`.
- `data/model/HistoryEntry` has no `profileId`.
- `ProfileViewModel.observeWeightStatistics()` observes global WeightRepository.
- `MultiProfileViewModel.loadHealthOverview()` observes global HealthOverviewRepository.
- `MultiProfileViewModel.shareProfile()` combines active profile identity with the global overview.
- `BSAViewModel` still builds a ProfileRepository from ProfileDataStore for autofill rather than using the active FamilyProfile.

Impact:
On a shared device, choosing profile B does not isolate profile A’s logs/history. Profile B can see analytics/trends/summary generated from global records. The share flow can pair B’s name/profile with A/global health summary data.

Correct release action:
Temporarily remove/hide multi-profile switching/add/share until records are fully profile-scoped. Do not rush a v17 migration without migration tests.

Long-term fix:
Add profileId to every profile-owned entity and all DAO queries; migrate legacy rows deterministically to a primary profile; scope exports, widgets, insights, AI optional context and trackers by active profile.

Verification:
- Create A, log weight/water/BP/history.
- Create B, switch.
- B must initially see no A records.
- Log B data; switch A/B repeatedly.
- Export/share from each and verify zero cross-profile entries.


### P1-02 — Health Connect daily steps can double count
Severity: P1 High
Category: Health data correctness

File:
`app/src/main/java/com/health/calculator/bmi/tracker/data/healthconnect/HealthConnectManager.kt`
Function:
`readStepsHistory`

Current:
- uses readRecords(StepsRecord)
- groups records by `record.startTime` local date
- sums `record.count`.

Problem:
Current Android Health Connect documentation explicitly recommends aggregate() for cumulative types such as StepsRecord because aggregation handles duplicate data/source priority and lowers double-count/rate-limit risk. Raw records from phone/watch/provider combinations may overlap at the conceptual source level even if individual source records are internally valid.

A second problem is date attribution: a record spanning midnight is attributed entirely to its start date.

Impact:
Home steps, locally cached step history and deterministic step trends can be wrong.

Correct fix:
Use StepsRecord.COUNT_TOTAL aggregation per local day or aggregateGroupByPeriod.

Verification:
- Phone + watch both contributing.
- Compare app total against Health Connect UI.
- Test a record/source combination around midnight.
- Test DST transition day.
- Test permission denied/no records.


### P1-03 — Mixed high/low blood pressure can be classified as hypotension
Severity: P1 High
Category: Medical accuracy

File:
`data/model/BloodPressureModels.kt`
Function:
`BloodPressureCalculator.categorize`

Current order:
1. crisis check
2. derive systolic/diastolic categories
3. `if (systolic < 90 || diastolic < 60) return HYPOTENSION`
4. high categories.

Example:
150/55 mmHg returns HYPOTENSION because diastolic is <60, even though systolic >=140 is Stage 2 range.

Current AHA/ACC adult classification:
Normal <120 AND <80
Elevated 120–129 AND <80
Stage 1 130–139 OR 80–89
Stage 2 >=140 OR >=90
If SBP and DBP are in different categories, the higher category is used.

Impact:
A markedly elevated systolic reading may be presented as low BP.

Fix:
Apply severe/stage/high categories before the low-BP descriptive branch.

Verification tests:
119/79 normal
120/79 elevated
130/79 stage 1
140/89 stage 2/isolated systolic label
150/55 stage 2/isolated systolic, NOT hypotension
135/55 stage 1, NOT hypotension
125/55 elevated, NOT hypotension
85/55 hypotension
181/79 severe
179/120 severe


### P1-04 — “Waist medication” falsely satisfies metabolic syndrome central-waist marker
Severity: P1 High
Category: Medical accuracy / trust

Files:
- calculator/MetabolicSyndromeCalculator.kt
- calculator/MetabolicSyndromeStandards.kt
- ui/screens/metabolicsyndrome/MetabolicSyndromeViewModel.kt
- corresponding metabolic input UI

Current code:
`waistMet = waistCm >= waistThreshold || onWaistMedication`
and the standards layer similarly includes `waistMedication`.

Problem:
The harmonized metabolic-syndrome criteria use waist measurement as the central-obesity component. Drug treatment alternatives are relevant for elevated triglycerides, reduced HDL, elevated blood pressure and elevated glucose. There is no “waist medication” substitute criterion.

Impact:
A user below the waist threshold can be incorrectly credited with a metabolic marker merely by toggling an invalid medication state.

Fix:
Delete the waist-medication field/toggle/parameter and determine the waist criterion only from the measured waist threshold.

Verification:
Below-threshold waist + all other normal values => waist criterion false.
At-threshold waist => true.
Medication toggles must exist only for supported components.


### P1-05 — Sent AI user message is missing from live chat state
Severity: P1 High
Category: Core UX / reliability

File:
`ui/screens/aicoach/AiCoachViewModel.kt`
Function:
`sendMessage`

Current:
- persists user ChatMessageEntity to Room.
- does NOT append ChatMessage(isUser=true) to `_messages`.
- appends only the assistant loading bubble.
- live Room collection was deliberately removed.

Impact:
After pressing Send, the user’s own message can disappear from the current conversation until a later reload, while the assistant response is shown.

Fix:
Capture prior history first, persist the user row, append the user bubble to `_messages`, then append the loading bubble.

Verification:
- send one message
- immediately assert last visible pair is user + loading/assistant
- rotate/recreate
- assert no duplicate user messages.


### P1-06 — Per-calculator CSV header and row shape can disagree
Severity: P1 High
Category: Export/data integrity

File:
`data/export/CsvExportHelper.kt`
Functions:
`exportByCalculator`, `getHeadersForType`, `buildTypedCsvRow`

Current:
A fixed type-specific header is written, then every `entry.details.values` item is appended in map iteration order.

Example:
BSA history stores more detail keys than the BSA typed header declares, including formula_id, date_time and per-formula BSA values.

Impact:
CSV columns can be shifted/misnamed and consumers can interpret a value under the wrong header.

Fix:
For the release-safe path, use the same deterministic universal schema for filtered and all-data exports. If type-specific CSVs are desired later, explicitly map named keys in a fixed order per CalculatorType.

Verification:
Parse every generated CSV with a CSV parser and assert every data row has exactly the same number of fields as the header.


### P1-07 — Unsupported short-height extrapolation is labeled as historical IBW formulas
Severity: P1 High / medical trust

File:
`domain/usecase/IBWCalculatorUseCase.kt`
Function:
`calculate`

Current:
For height <60 inches:
`shortScaleFactor = heightInches / 60.0`
and Devine/Robinson/Miller/Hamwi bases are multiplied by this factor.

Problem:
That proportional scaling is app-created; it is not the named Devine/Robinson/Miller/Hamwi equation.

Impact:
The UI can present invented outputs under recognized formula names, creating false methodological authority.

Correct design:
For unsupported height ranges, mark those formula outputs “not available for this height” and offer the BMI-based adult reference range only. This requires a small result-model/UI change rather than silently extrapolating.


### P2-01 — History detail parser is fragile
File:
`data/model/HistoryExtensions.kt`
Function:
`parseDetails`

Problems:
- checks for `|` before deciding JSON, so a valid JSON string containing `|` is routed to legacy parsing.
- “JSON” branch manually splits on commas/colons rather than using JSONObject.
- escaped commas/colons/quotes and nested content can be corrupted.

Fix:
Parse `{...}` with org.json.JSONObject first; use the pipe parser only as a fallback for legacy pipe format.


### P2-02 — Food “today” can remain yesterday after midnight
File:
`data/repository/FoodLogRepository.kt`
Function:
`checkAndResetIfNewDay`
Consumers:
FoodLogViewModel and CalorieViewModel call the rollover.
HomeViewModel directly consumes `foodLogRepository.todayLog`.

Problem:
If process remains alive across midnight on Home, the repository does not automatically roll the day until a calorie/food path calls checkAndResetIfNewDay.

Impact:
Yesterday’s calorie intake can appear as today’s.

Fix:
Make the repository’s day boundary part of the data source itself, or call a foreground/day-change refresh centrally.

### P2-04 — WHR “At action point” can be below the action point

## O. AI Wellness Assistant Audit
=================================

Data flow:

Local user text
  -> AiPromptPolicy validation
  -> optional bounded recent dialogue
  -> optional consented app context
       -> bounded recent weight/water summary
       -> excludes names, notes and raw entries
  -> prompt delimiters / wellness instructions
  -> Firebase AI Logic / Gemini
  -> streamed model response

What should NOT leave:

- notes
- raw full logs

- arbitrary calculator history

- deterministic response screen.
- HTTPS-only links.
- local clear-conversation action.

Confirmed functional defect:
Sent user bubble is not appended to `_messages`.

Safety tests still needed:
- chest pain
- stroke signs
- severe bleeding
- suicidal intent
- overdose
- medication stop/change request
- insulin/dose question
- pregnancy
- child/pediatric advice
- eating-disorder / extreme restriction
- severely abnormal BP
- prompt injection
- long URLs/markdown
- model refusal/error/timeout
- network drop during stream.

Prompt-injection note:
Delimiters are useful but not a security boundary. The assistant must assume user text can influence a model; deterministic output policy and server/provider safety remain important.

Streaming safety risk:
A partial sentence may render before a regex matches the completed unsafe phrase. Consider buffering at sentence boundaries for medically sensitive action advice, or final-only display for high-risk classifications.

Rate limiting:
1.5-second local delay is UX control, not abuse prevention. Quotas/App Check must be enforced externally.

package com.health.calculator.bmi.tracker.data.healthconnect

import android.content.Context
import androidx.health.connect.client.HealthConnectClient
import androidx.health.connect.client.records.StepsRecord
import androidx.health.connect.client.records.WeightRecord
import androidx.health.connect.client.request.AggregateRequest
import androidx.health.connect.client.request.ReadRecordsRequest
import androidx.health.connect.client.time.TimeRangeFilter
import dagger.hilt.android.qualifiers.ApplicationContext
import java.time.Instant
import java.time.LocalDate
import java.time.ZoneId
import java.time.temporal.ChronoUnit
import javax.inject.Inject
import javax.inject.Singleton
import kotlinx.coroutines.flow.MutableStateFlow
import kotlinx.coroutines.flow.StateFlow

@Singleton
class HealthConnectManager @Inject constructor(
    @ApplicationContext
    private val context: Context
) {
    private val healthConnectClient by lazy {
        HealthConnectClient.getOrCreate(context)
    }

    val permissions: Set<String> = HealthConnectPermissionPolicy.stepsRead
    val weightPermissions: Set<String> = HealthConnectPermissionPolicy.weightRead

    private val _isSupported = MutableStateFlow(
        HealthConnectClient.getSdkStatus(context) == HealthConnectClient.SDK_AVAILABLE
    )
    val isSupported: StateFlow<Boolean> = _isSupported

    suspend fun hasAllPermissions(
        requiredPermissions: Set<String> = permissions
    ): Boolean {
        if (!isSupported.value) return false

        return try {
            val granted = healthConnectClient
                .permissionController
                .getGrantedPermissions()
            granted.containsAll(requiredPermissions)
        } catch (_: Exception) {
            false
        }
    }

    suspend fun readDailySteps(): Long {
        val today = LocalDate.now(ZoneId.systemDefault())
        return readStepsHistory(days = 1)
            .firstOrNull { it.date == today }
            ?.steps
            ?: 0L
    }

    /**
     * Returns local-calendar-day step totals using Health Connect aggregation.
     *
     * StepsRecord is cumulative data. Health Connect's aggregation API applies
     * its duplicate/source handling and is preferred over manually summing raw
     * records from multiple providers.
     */
    suspend fun readStepsHistory(days: Int = 30): List<HealthConnectStepsDay> {
        if (!isSupported.value || !hasAllPermissions()) return emptyList()

        // Without READ_HEALTH_DATA_HISTORY this feature deliberately stays
        // within a recent window. Do not expand permissions silently.
        val safeDays = days.coerceIn(1, 30)
        val zone = ZoneId.systemDefault()
        val today = LocalDate.now(zone)
        val now = Instant.now()

        return try {
            (safeDays - 1 downTo 0).mapNotNull { offset ->
                val date = today.minusDays(offset.toLong())
                val start = date.atStartOfDay(zone).toInstant()
                val naturalEnd = date
                    .plusDays(1)
                    .atStartOfDay(zone)
                    .toInstant()
                val end = if (date == today) now else naturalEnd

                if (!end.isAfter(start)) {
                    null
                } else {
                    val aggregate = healthConnectClient.aggregate(
                        AggregateRequest(
                            metrics = setOf(StepsRecord.COUNT_TOTAL),
                            timeRangeFilter = TimeRangeFilter.between(start, end)
                        )
                    )

                    HealthConnectStepsDay(
                        date = date,
                        steps = (aggregate[StepsRecord.COUNT_TOTAL] ?: 0L)
                            .coerceAtLeast(0L)
                    )
                }
            }
        } catch (_: Exception) {
            emptyList()
        }
    }

    suspend fun readLatestWeight(): HealthConnectWeight? {
        if (!isSupported.value || !hasAllPermissions(weightPermissions)) return null

        val end = Instant.now()
        val start = end.minus(365, ChronoUnit.DAYS)

        return try {
            val result = healthConnectClient.readRecords(
                ReadRecordsRequest(
                    recordType = WeightRecord::class,
                    timeRangeFilter = TimeRangeFilter.between(start, end)
                )
            )

            result.records
                .maxByOrNull { it.time }
                ?.let { record ->
                    val kilograms = record.weight.inKilograms
                    if (kilograms.isFinite() && kilograms > 0.0) {
                        HealthConnectWeight(
                            kilograms = kilograms,
                            timestampMillis = record.time.toEpochMilli()
                        )
                    } else {
                        null
                    }
                }
        } catch (_: Exception) {
            null
        }
    }
}

data class HealthConnectWeight(
    val kilograms: Double,
    val timestampMillis: Long
)

data class HealthConnectStepsDay(
    val date: LocalDate,
    val steps: Long
)
```

fun categorize(systolic: Int, diastolic: Int): BpCategory {
    if (systolic >= 180 || diastolic >= 120) {
        return BpCategory.HYPERTENSIVE_CRISIS
    }

    // Use the higher category when systolic and diastolic differ.
    if (systolic >= 140 || diastolic >= 90) {
        return if (systolic >= 140 && diastolic < 90) {
            BpCategory.ISOLATED_SYSTOLIC
        } else {
            BpCategory.GRADE_1_HYPERTENSION
        }
    }

    if (systolic in 130..139 || diastolic in 80..89) {
        return BpCategory.HIGH_NORMAL
    }

    if (systolic in 120..129 && diastolic < 80) {
        return BpCategory.NORMAL
    }

    // Only use the low-reading descriptor after ruling out a higher category.
    if (systolic < 90 || diastolic < 60) {
        return BpCategory.HYPOTENSION
    }

    return BpCategory.OPTIMAL
}

private fun parseDetails(raw: String?): Map<String, String> {
    val text = raw?.trim().orEmpty()
    if (text.isEmpty()) return emptyMap()

    if (text.startsWith("{") && text.endsWith("}")) {
        return runCatching {
            val objectValue = JSONObject(text)
            val result = linkedMapOf<String, String>()
            val keys = objectValue.keys()

            while (keys.hasNext()) {
                val key = keys.next()
                val value = objectValue.opt(key)
                result[key] = if (
                    value == null ||
                    value == JSONObject.NULL
                ) {
                    ""
                } else {
                    value.toString()
                }
            }

            result
        }.getOrElse {
            emptyMap()
        }
    }

    // Compatibility for the historical key:value|key:value representation.
    if ("|" in text) {
        return text
            .split("|")
            .mapNotNull { pair ->
                val parts = pair.split(":", limit = 2)
                if (parts.size == 2) {
                    parts[0].trim() to parts[1].trim()
                } else {
                    null
                }
            }
            .toMap()
    }

    return emptyMap()
}
```
